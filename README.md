# پاسخ تمرین Git

**نام و نام خانوادگی:** سها صادقی  | **شماره دانشجویی:** 40031070

## سؤال ۱: تفاوت `merge` و `rebase`

هر دو دستور برای هماهنگ‌کردن تغییرات شاخه‌ها کاربرد دارند، اما شیوه ثبت تاریخچه در آن‌ها متفاوت است. `merge` مسیر توسعه دو شاخه را حفظ می‌کند و در صورت نیاز، یک کامیت ادغام به تاریخچه اضافه می‌کند. در `rebase`، کامیت‌های شاخه فعلی از نقطه جدیدی دوباره ساخته می‌شوند؛ به همین دلیل تاریخچه مرتب‌تر و خطی می‌شود، ولی شناسه کامیت‌های بازاعمال‌شده تغییر می‌کند.

برای ترکیب تغییرات یک شاخه تیمی با `main`، معمولاً `merge` انتخاب مطمئن‌تری است؛ چون نیازی به بازنویسی کامیت‌های مشترک ندارد. در مقابل، برای هماهنگ‌کردن شاخه‌ای که هنوز شخصی است با آخرین تغییرات `main` می‌توان از `rebase` کمک گرفت.

</div>

```bash
git switch main
git merge feature-profile

git switch feature-profile
git rebase main
```

## سؤال ۲: ثبت گزینشی تغییرات

گاهی چند بخش از یک فایل را ویرایش کرده‌ایم، اما نمی‌خواهیم همه آن‌ها در یک کامیت باشند. در خروجی `git diff`، مجموعه‌ای از خطوط تغییرکرده و خطوط زمینه اطرافشان را `hunk` می‌نامند. دستور زیر امکان بررسی و انتخاب جداگانه این بخش‌ها را فراهم می‌کند:

</div>

```bash
git add -p README.md
```

<div dir="rtl" align="right">

برای نمونه، اگر هم توضیحات اجرای پروژه و هم اطلاعات نویسندگان را تغییر داده باشیم، می‌توانیم فعلاً فقط تغییرات بخش اجرا را stage کنیم. هنگام انتخاب، `y` به معنای پذیرش بخش، `n` به معنای رد آن، `s` برای تقسیم بخش در صورت امکان و `e` برای ویرایش دستی patch است. پیش از ثبت کامیت نیز تغییرات انتخاب‌شده را کنترل می‌کنیم:

</div>

```bash
git diff --staged
git commit -m "Clarify project setup steps"
```

<div dir="rtl" align="right">

## سؤال ۳: تشخیص کامیت ایجادکننده خطا

وقتی یک قابلیت قبلاً درست کار می‌کرده و اکنون دچار مشکل شده است، `git bisect` برای پیدا کردن نقطه شروع خطا مناسب است. این دستور با روش جست‌وجوی دودویی، محدوده کامیت‌های مشکوک را در هر مرحله کوچک‌تر می‌کند.

ابتدا کامیت فعلی را معیوب و یک کامیت قدیمیِ مشخص را سالم معرفی می‌کنیم:

</div>

```bash
git bisect start
git bisect bad
git bisect good <known-good-commit>
```

<div dir="rtl" align="right">

سپس Git کامیتی را برای آزمایش انتخاب می‌کند. اگر مشکل در آن وجود نداشت، `git bisect good` و در غیر این صورت `git bisect bad` را اجرا می‌کنیم. پس از شناسایی نخستین کامیت معیوب، با دستور زیر از حالت بررسی خارج می‌شویم:

</div>

```bash
git bisect reset
```

<div dir="rtl" align="right">

در نتیجه لازم نیست همه کامیت‌های بین دو نسخه را به ترتیب بررسی کنیم.

## سؤال ۴: کنترل وضعیت فایل‌ها پیش از ثبت

**۱.** برای دیدن فایل‌های تغییرکرده و وضعیت staging از `git status` استفاده می‌کنیم. `git diff` تغییرات stageنشده را نسبت به index نشان می‌دهد و `git diff --staged` محتوای آماده ثبت را با آخرین کامیت مقایسه می‌کند.

</div>

```bash
git status
git diff
git diff --staged
```

<div dir="rtl" align="right">

**۲.** اگر ابتدا `README.md` را stage کنیم و پس از آن دوباره همان فایل را ویرایش کنیم، اجرای معمولی `git commit` فقط نسخه‌ای را ثبت می‌کند که در staging قرار دارد. ویرایش‌های جدیدتر همچنان خارج از کامیت باقی می‌مانند.

**۳.** برای جلوگیری از اضافه شدن فایل‌های موقت پوشه `tmp` در ریشه مخزن، الگوی `/tmp/` را در `.gitignore` می‌نویسیم. این تنظیم فایل‌هایی را که از قبل tracked شده‌اند، خودکار از Git خارج نمی‌کند. برای توقف ردیابی چنین فایلی بدون پاک کردن نسخه محلی می‌توان از `git rm --cached` استفاده کرد.

## سؤال ۵: مدیریت تداخل هنگام ادغام

**۱.** اگر در دو شاخه، محتوای یک قسمت از `README.md` به شکل ناسازگار تغییر کند، Git ممکن است نتواند نسخه نهایی را خودکار تعیین کند. تغییر دادن قسمت‌های متفاوت یک فایل، لزوماً به معنی ایجاد conflict نیست.

**۲.** پس از شروع ادغام، دستور `git status` فایل‌هایی را که نیاز به حل تداخل دارند مشخص می‌کند:

</div>

```bash
git switch main
git merge feature-readme
git status
```

<div dir="rtl" align="right">

**۳.** در فایل دارای conflict، متن دو نسخه را بررسی کرده و محتوای درست را، در صورت نیاز با ترکیب هر دو، نگه می‌داریم. نشانه‌های تداخل مانند `<<<<<<<`، `=======` و `>>>>>>>` باید از فایل حذف شوند. پس از بررسی نتیجه، ادغام را تکمیل می‌کنیم:

</div>

```bash
git diff --check
git add README.md
git merge --continue
```

<div dir="rtl" align="right">

**۴.** اگر بخواهیم از ادغام انجام‌نشده صرف‌نظر کنیم، `git merge --abort` برای لغو فرایند استفاده می‌شود. در صورتی که پیش از ادغام تغییر محلی مزاحمی نداشته باشیم، معمولاً وضعیت قبلی مخزن بازگردانده می‌شود.

## سؤال ۶: روش درست بازگردانی تغییرات

**۱.** زمانی که فقط می‌خواهیم ویرایش‌های stageنشده فایل `notes.txt` را حذف کنیم، از دستور زیر استفاده می‌کنیم:

</div>

```bash
git restore notes.txt
```

<div dir="rtl" align="right">

این دستور محتوای working tree را از staging جایگزین می‌کند. با فرض سؤال که staging با آخرین کامیت یکسان است، فایل به همان محتوای آخرین کامیت بازمی‌گردد؛ بدون تغییر در تاریخچه یا سایر فایل‌ها.

**۲.** اگر تغییرات را به اشتباه stage کرده باشیم و فقط قصد خارج کردن آن‌ها از staging را داشته باشیم، دستور مناسب چنین است:

</div>

```bash
git restore --staged notes.txt
```

<div dir="rtl" align="right">

این بار محتوای محلی فایل حفظ می‌شود و فقط نسخه ثبت‌شده در index به آخرین کامیت برمی‌گردد.

**۳.** برای خنثی کردن یک کامیت اشتباه که قبلاً در شاخه مشترک `main` منتشر شده است، بهتر است به جای دستکاری تاریخچه، یک کامیت معکوس ایجاد کنیم:

</div>

```bash
git revert <bad-commit-hash>
git push origin main
```

<div dir="rtl" align="right">

`revert` اثر تغییرات کامیت مشخص‌شده را برمی‌گرداند، ولی خود آن کامیت در تاریخچه می‌ماند. به همین دلیل نسبت به `reset` همراه با `force push` برای همکاری تیمی کم‌خطرتر است.
