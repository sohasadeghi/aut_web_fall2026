# تمرین عملی HTTP

**درس:** مهندسی اینترنت  
**موضوع:** پیاده‌سازی Reverse Proxy با احراز هویت JWT

در این تمرین، یک سرویس قدیمی را پشت پراکسی قرار داده‌ام تا کاربران نتوانند بدون احراز هویت به آن دسترسی پیدا کنند. برای سرویس قدیمی از ایمیج `ghcr.io/mccutchen/go-httpbin:2.25.0` استفاده شده است. پراکسی با Go نوشته شده و سرویس‌ها با Docker Compose اجرا می‌شوند.

مسیر درخواست‌ها به این شکل است:

```text
Client --> Reverse Proxy (port 80) --> go-httpbin (port 8081)
                  |
                  +--> JWT نامعتبر یا موجود نبودن توکن: 401
```

## ۱. اجرای سرویس فقط در شبکه داخلی

برای اینکه یک سرویس از اینترنت قابل دسترسی نباشد، می‌توان آن را روی IP داخلی اجرا کرد و با تنظیم فایروال، دسترسی به پورت آن را محدود کرد. در Docker هم لازم نیست پورت سرویس روی سیستم میزبان منتشر شود. کافی است سرویس در یک شبکه داخلی قرار بگیرد و فقط برنامه‌هایی که به آن شبکه متصل هستند، بتوانند با آن ارتباط برقرار کنند.

در فایل `compose.yaml`، سرویس `legacy` فقط به شبکه `private` وصل است و پورت `8081` آن با `ports` منتشر نشده است. در مقابل، پراکسی به هر دو شبکه `public` و `private` متصل است. در نتیجه، درخواست‌ها ابتدا به پراکسی می‌رسند و بعد از بررسی توکن به سرویس قدیمی فرستاده می‌شوند. البته برای استفاده در شبکه واقعی، تنظیمات فایروال و دسترسی‌های سرور هم باید بررسی شوند.

## ۲. توضیح TLS Termination

بعضی از سرویس‌های قدیمی از HTTPS پشتیبانی نمی‌کنند یا اضافه‌کردن آن به خود برنامه دشوار است. در روش TLS Termination، ارتباط HTTPS بین کاربر و Reverse Proxy برقرار می‌شود. پراکسی گواهی TLS را مدیریت می‌کند، داده‌های دریافتی را رمزگشایی می‌کند و درخواست را به سرویس داخلی می‌فرستد.

مزیت این روش این است که بدون تغییر اساسی در سرویس قدیمی می‌توان ارتباط کاربر تا پراکسی را رمزنگاری کرد و مدیریت گواهی‌ها را در یک نقطه انجام داد. بااین‌حال، اگر ارتباط پراکسی با سرویس داخلی HTTP باشد، آن بخش از مسیر رمزنگاری نشده است؛ بنابراین شبکه داخلی هم باید امن باشد یا برای آن مسیر از TLS استفاده شود. TLS Termination جای احراز هویت را هم نمی‌گیرد و باید جداگانه بررسی شود.

در این تمرین، مطابق صورت سؤال، پراکسی روی پورت `80` با HTTP پیاده‌سازی شده است و TLS Termination فقط توضیح داده می‌شود. برای در دسترس قرار دادن چنین سرویسی روی اینترنت واقعی، باید HTTPS هم فعال شود؛ چون ارسال JWT روی HTTP امن نیست.

## ۳. پیاده‌سازی JWT Authentication Proxy

### ابزارهای موردنیاز

برای اجرای پروژه به Docker و Docker Compose نیاز است. برای آزمایش درخواست‌ها از `curl` و برای ساخت کلید از `openssl` استفاده می‌کنم. نصب Go فقط زمانی لازم است که بخواهیم تست‌های واحد را خارج از Docker اجرا کنیم.

### اجرای پروژه

ابتدا در پوشه پروژه، فایل `.env` را با یک کلید تصادفی می‌سازیم:

```bash
printf 'JWT_SECRET=%s\nBIND_IP=127.0.0.1\nPROXY_PORT=80\n' "$(openssl rand -hex 32)" > .env
```

سپس سرویس‌ها را اجرا می‌کنیم:

```bash
docker compose up -d --build
docker compose ps
```

پراکسی از طریق `http://localhost` در دسترس است، ولی پورت `8081` سرویس قدیمی روی میزبان منتشر نمی‌شود. مقدار `127.0.0.1` در فایل `.env` باعث می‌شود پورت پراکسی هم در این آزمایش فقط از همان سیستم قابل دسترسی باشد. اگر پورت `80` اشغال است، می‌توان `PROXY_PORT` را در `.env` برابر `8080` قرار داد و در دستورهای بعدی از `http://localhost:8080` استفاده کرد.

### آزمایش درخواست بدون توکن

```bash
curl -i http://localhost/get
```

چون هدر `Authorization` فرستاده نشده است، پراکسی باید پاسخ `401 Unauthorized` برگرداند.

### ساخت توکن آزمایشی

برای آزمایش، یک ابزار ساده در مسیر `cmd/mint` قرار دارد که با کلید موجود در `.env` توکن JWT می‌سازد:

```bash
TOKEN=$(docker compose run --rm --no-deps --entrypoint /mint proxy -sub student)
```

توکن با الگوریتم `HS256` امضا می‌شود و به‌صورت پیش‌فرض ۱۵ دقیقه اعتبار دارد. این ابزار فقط برای آزمایش محلی است و سیستم ورود کاربران محسوب نمی‌شود.

### آزمایش درخواست با توکن معتبر

```bash
curl -i -H "Authorization: Bearer $TOKEN" http://localhost/get
```

اگر توکن معتبر باشد، درخواست به `go-httpbin` می‌رسد و باید پاسخ `200 OK` همراه با داده JSON دریافت شود. برای آزمایش یک درخواست POST نیز می‌توان از دستور زیر استفاده کرد:

```bash
curl -i -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"message":"hello"}' \
  http://localhost/post
```

### آزمایش توکن نامعتبر

```bash
curl -i -H 'Authorization: Bearer invalid.token.value' http://localhost/get
```

در این حالت هم باید پاسخ `401 Unauthorized` دریافت شود. پراکسی امضای توکن، الگوریتم، صادرکننده، مخاطب و زمان اعتبار آن را بررسی می‌کند. بعد از تأیید نیز هدر `Authorization` را از درخواستی که به سرویس قدیمی می‌فرستد حذف می‌کند.

اگر سرویس داخلی در دسترس نباشد، پراکسی پاسخ `502 Bad Gateway` برمی‌گرداند.

### تست‌ها و پایان کار

برای اجرای تست‌های واحد، در صورت نصب بودن Go از دستور زیر استفاده می‌کنیم:

```bash
go test ./...
```

برای متوقف‌کردن سرویس‌ها:

```bash
docker compose down
```

### ساختار فایل‌ها

```text
.
├── compose.yaml
├── Dockerfile
├── go.mod
├── cmd/
│   ├── proxy/main.go
│   └── mint/main.go
├── internal/
│   ├── gateway/
│   │   ├── proxy.go
│   │   └── proxy_test.go
│   └── jwtauth/
│       ├── jwt.go
│       └── jwt_test.go
└── README.md
```

در `cmd/proxy`، سرور HTTP اجرا می‌شود. کد بررسی و ساخت JWT در `internal/jwtauth` قرار دارد و بخش `internal/gateway` پس از اعتبارسنجی توکن، درخواست را به سرویس داخلی منتقل می‌کند. فایل‌های `*_test.go` نیز حالت‌های معتبر و نامعتبر را بررسی می‌کنند.

**نکته امنیتی:** در این پروژه از یک کلید مشترک برای امضا و بررسی JWT استفاده شده است. در سرویس واقعی باید مدیریت کاربران، نگهداری و تعویض کلیدها، ابطال دسترسی و HTTPS هم در نظر گرفته شود. فایل `.env` و توکن‌های ساخته‌شده نباید در GitHub قرار بگیرند.
